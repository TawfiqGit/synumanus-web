Refondre avec discernement

Une refonte n’est pas forcément une reconstruction totale.

Le bon choix dépend de l’état du code, du produit, du backend, des stores et des priorités métier. Une réécriture complète peut être pertinente — mais elle doit être une conclusion d’audit, jamais un réflexe.

01

L’application devient lente

Démarrages longs, écrans lourds, crashs ou comportements instables dégradent l’usage et rendent les évolutions risquées.

02

L’UX ne suit plus le métier

Le produit a grandi par ajouts successifs et les parcours reflètent l’historique plutôt que les usages actuels.

03

La stack devient fragile

Dépendances anciennes, versions de SDK, architecture ou dette technique rendent chaque changement plus coûteux.

04

Le produit a changé

La proposition de valeur, les utilisateurs ou le modèle métier ont évolué et l’application n’est plus alignée.

Trois stratégies possibles

Conserver, refactoriser ou reconstruire. Le diagnostic décide.

Le but n’est pas de maximiser la quantité de code neuf, mais de retrouver une base saine au coût et au risque raisonnables.

01 · Moderniser

Conserver & moderniser

Lorsque le socle reste valable, on peut mettre à niveau dépendances, SDK, composants et parcours sans démolir le produit.

  • Mises à niveau
  • Correctifs ciblés
  • UX progressive
02 · Restructurer

Refactoriser par zones

Quand certaines parties bloquent l’évolution, elles peuvent être isolées et remplacées progressivement.

  • Architecture par étapes
  • Réduction de dette
  • Continuité du service
03 · Reconstruire

Repartir sur un nouveau socle

Si l’existant est devenu trop coûteux ou incompatible avec la cible, une reconstruction peut être préparée avec migration contrôlée.

  • Nouveau socle
  • Migration données/API
  • Bascule préparée

Une application mobile n’est pas seulement son code client. Une refonte sérieuse regarde aussi l’API, les données, les comptes stores, les dépendances et les conditions de migration.

Questions fréquentes

Avant de lancer une refonte.

Une bonne reprise évite deux excès : bricoler indéfiniment un socle fragile ou jeter trop vite ce qui fonctionne encore.

Faut-il forcément réécrire l’application ?+

Non. Une reprise peut être une mise à niveau, un refactor ciblé, une refonte UX, une migration progressive ou une reconstruction. Le choix dépend de l’audit.

Pouvez-vous reprendre une application développée par une autre équipe ?+

Oui, si les accès nécessaires sont disponibles : code source, comptes stores, backend/API et éléments de configuration utiles. La première étape consiste à évaluer l’état réel de l’existant.

Peut-on garder les comptes App Store et Google Play existants ?+

En principe, une refonte vise à préserver la continuité de publication quand c’est possible. Les identifiants d’application, signatures et accès stores doivent être examinés pendant l’audit.

Que devient le backend pendant la refonte ?+

Il peut être conservé, adapté ou remplacé selon son état et les objectifs. Le mobile et le backend doivent être étudiés ensemble lorsqu’ils sont fortement couplés.

Comment éviter une interruption pour les utilisateurs ?+

En préparant une stratégie de migration : compatibilité API, données, versions intermédiaires, tests, publication et bascule progressive lorsque le contexte le permet.
